# SUMO 생성기 v3 시나리오 → 학습 공장 투입 결과 (2026-08-18, 민서)

현준의 부탁 ①②③에 대한 결과. 숫자만 먼저, 해석은 아래.

## 부탁 ① — 트리(risk_model_streams.json), 팀 명령 그대로

입력: SUMO v3 시나리오 700개(scenario_9001~9700) × 최근접 쌍 2 = **1,401 스트림** + `--from-scenario-sim 4000 --families --randomize`
학습셋: 3,411,227행 / 5,401 시나리오 (`training_dataset_streams.csv`, 미푸시·재생성 가능)

| 평가 범위 | 위험 시나리오 | 적시경보 규칙 → 모델 | 오경보 규칙 / 모델 |
|---|---|---|---|
| **전체** | 412 | **55.3% → 61.7%** | 2.04% / 2.04% |
| SUMO(실차 5~25 m/s) | 330 | 53.9% → **69.1%** (+15.2p) | 1.92% / 3.50% |
| scenario_sim(RC 스케일) | 82 | 61.0% → **31.7%** (−29.3p) | 2.15% / 0.74% |

## 부탁 ② — transformer(최근 10프레임, 입력 15열 그대로, 정답 y_train)

`train_alarm_transformer.py` → `models_alarm_tf/alarm_transformer.onnx` (+ scaler JSON, 입력 [batch,10,15], ONNX 오차 1.5e-7)
같은 CSV, 같은 분할, 같은 오경보율(2.17%)에서:

| 평가 범위 | 적시경보 규칙 → transformer |
|---|---|
| **전체** | 56.6% → **54.6%** (규칙보다 낮음) |
| SUMO | 54.0% → 60.9% |

## 해석 (중요)

1. **전체 숫자만 보면 안 됨.** 트리 +6.4p, transformer −2.0p 는 둘 다 "실차 쪽으로 쏠린" 결과다.
   SUMO 위험 시나리오(1,099)가 RC 위험 시나리오(274)의 4배라 두 모델 모두 실차 속도대를 우선 배웠고,
   **RC 스케일(실기 환경)에서는 규칙보다 크게 나빠졌다.** 이 두 모델은 그대로 젯슨 실기에 올리면 안 된다.
2. transformer 가 트리를 못 이긴 것은 첫 시도(6 epoch, 하이퍼파라미터 그대로)라 결론짓기 이르다.
   다만 "쏠림"이라는 구조적 문제는 모델 종류와 무관하게 동일하게 나타났다 → 데이터 배합이 먼저다.
3. SUMO 만 보면 실차 속도를 처음 배운 효과는 분명하다(트리 +15p). 배합만 맞추면 살릴 수 있는 재료.

## 발견한 버그 (팀 코드, 안 고침 — 현준이 판단)

`build_dataset_from_streams.py --streams … --from-scenario-sim … --train` 을 **같이** 주면 학습 단계에서
`dataset.split_by_scenario` 의 `sorted(ids)` 가 `str`(sumo id) vs `int`(scenario_sim id) 비교로 죽는다.
데이터셋 CSV 는 그 전에 저장되므로 `train_streams_model.py` 로 학습만 다시 돌리면 된다.
근본 수정은 `build_from_streams_dir` / `build_from_scenario_sim` 에서 `scenario_id` 를 `str` 로 통일하면 끝.

## 추가 (같은 날 저녁) — (a) SUMO 축소 8:2 배합 결과 → RC에서 규칙 이김

현준 지시대로 (a)만 먼저: `sumo_batch_to_streams.py --pairs 1 --limit 90` (SUMO 위험 75) + scenario_sim 4000 (RC 위험 274) ≈ **RC 8 : SUMO 2**.
`training_dataset_streams_82.csv` (1,878,375행 / 4,090 시나리오) → `risk_model_streams_82.json` (임계값 0.8380, 규칙 오경보 2.18% 기준).

| 평가 범위 | 위험 시나리오 | 적시경보 규칙 → 모델 | 오경보 규칙 / 모델 | (이전 4:1 SUMO 우위) |
|---|---|---|---|---|
| **전체** | 105 | **55.2% → 62.9%** (+7.7p) | 2.18% / 2.18% | 55.3 → 61.7% |
| **scenario_sim (RC)** | 81 | **58.0% → 61.7%** (+3.7p) ✅ | 2.23% / 2.03% | 61.0 → 31.7% ❌ |
| SUMO (실차) | 24 | 45.8% → 66.7% (+20.9p) | 1.32% / 4.86% | 53.9 → 69.1% |

- 쏠림 해소: RC 가 규칙 위로 올라왔고 SUMO 이득(+21p)도 유지. RC 오경보는 오히려 감소.
- **`risk_model_streams_82.json` = 배포 후보.** 단 RC +3.7p 는 위험 81개 기준이라 큰 차이는 아님 — "규칙보다 나빠지지 않으면서 실차 속도를 배웠다"가 정확. 실기 켤지는 오늘 대본 라벨 현장 점수로 판단.
- (b) 가중치 / (c) 속도대 분리 / transformer 스윕은 현준 지시대로 미룸 — (a)로 목표 달성.
- 재현: 위 두 명령 + `train_streams_model.py --csv training_dataset_streams_82.csv --model risk_model_streams_82.json` + `eval_streams_by_source.py --csv … --model …`.

## 추가 2 — 현준 지시 ①② (2026-08-18 밤)

### ① 82 모델을 8/17 실측 raw 로그로 채점 (`field_score_82.py`)

**대본 라벨 파일은 저장소에 없다** (2026-08-18 기준; 8/18 raw 로그도 없음). 있는 것은 `data/젯슨로그_20260817/raw_*.log` 20개(비어있지 않은 것)와
`data/듀얼시리얼기록/260817{코너1~4,평행1}_*/` 세션명뿐. 그래서 라벨 없이 되는 채점을 했다:
실측 로그를 `stream_to_features`(젯슨 실행 코드 경로 그대로)로 흘려 15열을 만들고, 그 위에서 규칙 vs 모델을 나란히.
"접근 에피소드"는 replay_0817.py 와 같은 휴리스틱(거리<8 m·차량속도≥0.4, 3 s 끊김 분리) — 대본이 오면 `--labels session,t_start,t_end,event` 로 대체 가능.

9 세션 합산 (130,843행, 정지 62,639행, 접근 에피소드 108, 재획득 198):

| | 경보율 | 정지 오경보 | 접근 검출 | 적시(T_floor 앞) | 재획득 직후 유령 |
|---|---|---|---|---|---|
| 규칙 | 1.32% | 0.13% | 37/108 | 16/108 | 6/198 |
| **82 모델** | 1.12% | 0.13% | 34/108 | 14/108 | 6/198 |
| 4:1 모델(참고) | 1.46% | 0.10% | 36/108 | 14/108 | 6/198 |

→ **실측에선 82 모델 ≈ 규칙 (약간 아래).** 시뮬 RC +3.7p 는 현장에서 안 보였다. 나쁘지도 않다(오경보·유령 동일, 검출 3건 차이).
단 접근 에피소드가 휴리스틱이라 "실제 위험"과 다를 수 있음 → 대본 라벨로 재채점 필요. `results/field_score_0817.csv`, `results/field_features_0817.csv`(15열+proba, 재채점용).

### ② 82 배합에 GPS 튐 강조 잡음 켜고 재학습 (`run_with_gps_jump.py`, `--gps-jump`)

먼저 확인한 사실: **82 모델은 이미 GPS 튐이 든 데이터로 학습돼 있었다.** `--randomize` = `FieldNoiseParams.randomized()` = 8/17 실측 기반
(무효 0~4회/분·3~8 s, 재획득 점프 0~20 m, float32 격자, 손실 0~15 %). 다만 하한이 0 이라 튐 없는 시나리오도 섞임.
그래서 튐 4개 하한을 실측 수준으로 올린 프리셋(무효 ≥1.5/분, 지속 상한 5~8 s, 점프 5~20 m)을 몽키패치로 주입(팀 코드 무수정)해
같은 8:2 배합으로 재학습 → `risk_model_streams_82jump.json` (임계값 0.8043).

| | 시뮬 RC 적시경보 | 시뮬 SUMO | **실측 정지 오경보** | 실측 접근 검출 | 실측 유령 |
|---|---|---|---|---|---|
| 규칙 | 61.3% | 50.0% | 0.13% | 37/108 | 6/198 |
| 82 | 61.7%(전 배합) | 66.7% | 0.13% | 34/108 | 6/198 |
| **82jump** | 62.7% | 70.8% | **2.64% (20배↑)** | 47/108 | 9/198 |

→ **82jump 는 배포 불가.** 시뮬에선 82 와 비슷하지만 실측에서 정지 오경보가 0.13→2.64 %로 폭증 — 튐을 항상 크게 넣으니
"정지 상태 격자 잡음"을 접근으로 배웠다. 8/17 에 현준이 가장 문제 삼은 증상(정지 유령 경보)이 그대로 재발.
검출은 늘었지만(47/108) 오경보 대가가 너무 큼. 교훈: 잡음은 "항상 최악"이 아니라 randomized 처럼 **분포로** 넣는 게 맞았다 (82 가 그 상태).
