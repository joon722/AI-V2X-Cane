# 다중 차량 추적 — 차가 여러 대일 때 차마다 따로 판정 (2026-10-05, 최민서)

## 1. 문제: 차가 2대 오면 한 대만, 그것도 섞여서 추적됐다

- `step4_state_store.py` `StateStore.update()`가 `self.latest[node_type] = row` — 노드 **종류**마다 한 칸.
  차 A·B의 패킷이 같은 `"vehicle"` 칸을 번갈아 덮어쓴다.
- `step6_kinematics.py`의 차량 칼만 추적기도 `"vehicle"` 하나 → A 위치와 B 위치 사이를 오가고,
  점프 게이트에 걸려 트랙이 계속 재시작되거나, 거리 미분이 두 차를 섞어 가짜 접근속도·TTC가 나온다
  (v4.1에서 고친 "최근접 보행자 교체 시 거리 미분" 버그와 같은 종류).
- `step8_send_risk.py`는 등급 하나를 `target_id=0`으로 방송, RSU 브리지(`v2x_bridge.ino`)도 target_id를 무시.
- SUMO 쪽도 `sim_to_rsu_stream.py`가 (차 1대, 보행자 1명) 쌍만 만들어서 이 상황이 시험에 한 번도 안 나왔다.
  그런데 SUMO 시나리오 150개를 세어 보니 **모든 시나리오에** "15 m 안으로 10초 안에 2대 이상 오는" 묶음이 있었다
  (684묶음, 2~9대).

합성 2대 예 (A는 5 s, B는 10.5 s에 지팡이 옆 1 m 통과, 3~10 s 동시 송신):

| | A 접근(2~5 s) | B 접근(7.5~10.5 s) |
|---|---|---|
| 기존 step8 | L3 후 **4.06 s에 0으로 꺼짐**(A 통과 1초 전) | 10.26 s에야 L2 (통과 0.24초 전) |
| 다중 차량 | 3.03 s부터 L3 유지 | 8.56 s부터 L3 (통과 2초 전) |

## 2. 고친 방식: 차량 node_id마다 "차선" — 기존 step4~8 판정 로직은 그대로

`step8_multi_vehicle.py` (신규). 차선 하나 = 기존 step8 한 벌(StateStore + KinematicsPipeline + RiskSender:
칼만·EMA·도플러 상한·거리추세·UWB·홀드·gap-hold 전부).

```
지팡이 행 ──► 모든 차선          차선 A (차 A vs 지팡이) ─► 등급 A ─┐
차량 행   ──► 그 node_id 차선    차선 B (차 B vs 지팡이) ─► 등급 B ─┼─► max ─► 지팡이 다운링크
uwb 행    ──► 보낸 차 차선       ...                                 ┘
```

- 차가 한 대면 기존 step8과 **등급 변화 시점까지 동일** (테스트로 고정).
- 새 차선은 지팡이 최근 10초 이력으로 준비(prime) — 안 하면 걷는 보행자의 지팡이 속도 추정을 처음부터
  다시 배워 "그 차만 있었을 때"와 판정이 어긋났다(SUMO 42구간 중 1개).
- 한 차선의 예외는 그 차선 안에서 끝난다(다른 차 경보·지팡이 다운링크는 계속).
- 차가 30초 조용하고 등급 0이면 차선을 닫는다. 판정이 4초(gap-hold 3 s + 홀드 1 s) 넘게 없는 차선의 등급은 0으로 본다.

다운링크 (`--downlink`)

| 모드 | 동작 | 언제 |
|---|---|---|
| `max` (기본) | 차선 등급 최댓값 하나를 target_id=0 방송 → 어느 차든 위험하면 지팡이·모든 차 스피커가 울림 | **지금 브리지 그대로** |
| `per-target` | 차에는 자기 등급(target_id=차 id), 지팡이에는 최댓값(target_id=지팡이 id) | 브리지가 target_id대로 보내는 펌웨어로 바뀐 뒤에만 |

기록: 집계 CSV(`--csv`, step8 열 + `vehicle_id, n_vehicles, vehicle_levels`, 행 내용은 가장 위험한 차)
+ 차량별 CSV(`<csv 이름>_vehicles/veh_<id>.csv`, step8과 같은 열). stream_live는 `logs/*.csv`만 보므로 영향 없음.

## 3. 검증

### 3.1 단위 테스트 — `test_step8_multi_vehicle.py` 14개 통과, 전체 459 통과
(기존 실패 1개 `test_build_dataset_from_streams::test_scenario_sim_source...`는 수정 전부터 있던 것 — 이번 변경과 무관)

### 3.2 SUMO 재생 — `auto_pipeline/eval_multi_vehicle.py`

같은 잡음 패킷(gps_noise 기본 잡음, 노드마다 독립 난수)을 셋으로 재생. 모델 OFF(규칙만), 나머지 step8 기본값.

- **기준**: 차 한 대 + 지팡이만 남긴 스트림 → 기존 step8 ("그 차만 있었다면 울렸을 경보")
- **기존**: 모든 차 → 기존 step8 (한 칸 덮어쓰기)
- **다중**: 모든 차 → step8_multi_vehicle (max)

v5data(생성기 v3) 앞쪽 시나리오에서 묶음 300개 — 차 1,076대, 재생 143.5분 (`multi_vehicle_eval/summary.txt`, `per_vehicle.csv`):

| 지표 | 기준(차별 단독) | 기존(칸 1개) | **다중(차선)** |
|---|---|---|---|
| "그 차만 있었다면 울렸을" 경보 구간 유지 (1,060구간, 차 750대) | 1,060 | 269 (**25.4%**) | **1,060 (100%)** |
| 경보를 하나라도 놓친 차 | — | 593대 | **0대** |
| 참값 3 m 안 근접 통과 218대: 최근접 3초 전~최근접에 L2+ | 163 (74.8%) | 58 (26.6%) | **187 (85.8%)** |
| 가짜 경보 (어느 차 기준도 L2+ 아닌데 지팡이 L2+) | — | 78.4초 (0.91%) | **0.0초** |

동시에 온 차 수별 경보 유지율 (기존 → 다중): 2대 43.7% → 100%, 3대 27.6% → 100%, 4대 22.2% → 100%, 5대 이상 14.4% → 100%.

읽는 법
- 기존 방식은 차가 여러 대면 **경보 4개 중 3개를 잃었다.** 다른 차 패킷이 칸을 덮어쓰면서 접근속도가 사라지거나
  트랙이 재시작돼 TTC가 안 나오고, 반대로 두 차를 섞은 가짜 접근으로 엉뚱한 때 울리기도 했다(0.91%).
- 다중 방식은 차선마다 "그 차만 있을 때"와 똑같이 판정하므로 유지율 100%, 가짜 경보 0이다.
- 근접 통과 85.8%가 기준 74.8%보다 높은 것은 더 잘 잡아서가 아니라, 다른 차 때문에 이미 울리고 있던 경보가
  겹친 몫이다(최댓값 방송). 기준 74.8% 자체(단일 차량 판정이 잡음 속 근접 통과 4대 중 1대를 늦게 잡음)는
  이번 수정 범위 밖 — 기존 규칙·잡음 문제다.

## 6. 남은 일

1. **RSU 브리지 펌웨어(현준 님 확인 필요)**: `per-target`을 쓰려면 브리지가 `{"target_id":X,"risk":N}`의 X로
   보내야 한다(MSG_RISK_ALERT의 target_id에 싣거나 해당 MAC으로 유니캐스트). 지팡이·차량 V5 펌웨어는
   target_id 필터가 이미 있다. 옛 `arduino/10_rsu_espnow_multi_jetson_bridge`에 장치 표·target 전송 로직이 있다(프로토콜 v2라 그대로는 못 씀).
   그 전까지는 `max` — 다른 차 때문에 내 차 스피커도 울리는 것은 감수.
2. 차량 GPS 바이어스(`calibrate_bias.py`)는 차 한 대 기준 값을 모든 차에 적용 중 → 차별 보정 필요(경고 로그 남김).
3. 화면(live_state/stream_live)은 가장 위험한 차 한 대만 보여 준다. 여러 대 표시는 화면 쪽 작업.
4. 학습 공장(`sumo_batch_to_streams.py`)은 여전히 쌍 단위 — 판정이 차선별이라 학습 데이터 형식은 그대로 맞다.
