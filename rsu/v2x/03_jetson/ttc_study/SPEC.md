## 0. 한 장 요약

| | 적시 경보 | 오경보율 |
|---|---|---|
| A. 현 점수표 (`step7_risk`) | 66.6% ±5.2 | **1.99%** |

> 규칙은 조용하지만 늦고, TTC 규칙은 빠르지만 시끄럽다.

## 1. 왜 시작했나

팀 질문은 *"공모전 주제가 AI인데 판단의 핵심이 rule 기반 점수표 아닌가"* 였다.
그 지적이 맞았고, 파고들자 더 근본적인 문제가 나왔다.

**기존 AI 모델은 규칙을 베낀 모델이었다.** `auto_pipeline/build_training_dataset.py`가
학습 라벨을 이렇게 만든다.

```
정답 = 팀 점수표(TTC 구간별 점수) × DCPA 게이트
```

정답지를 규칙으로 만들어놓고 그 규칙을 학습시켰으니, 모델에게 "TTC 2초가 맞나"를
물어도 답할 수 없다. `AI_Model/transformer/build_v3_and_baseline.py`도 채점표를
동결 사본으로 들고 있어 v1→v2→v3 내내 같은 구조다. **모델은 계속 좋아졌는데
정답지는 한 번도 바뀌지 않았다.**

거기에 `scaler.json`의 입력 피처에 `risk_score`가 들어 있다 — 답을 문제지에
적어둔 것이라 정확도 수치가 의미를 잃는다.

즉 팀의 지적("출력이 규칙이다")과 진단 결과("학습 데이터가 규칙이다")는 같은 문제의
앞뒤였고, 해결책도 하나였다: **규칙과 무관한 정답을 만든다.**

## 2. 구조

```
  ② 상한 게이트 (절대 규칙)    멀고 접근하지 않음 -> 무조건 레벨 0
  ─────────────────────────────────────────────────────────
  ① AI 조건부 판단             상황마다 다른 기준으로 판단
  ─────────────────────────────────────────────────────────
  ⓪ 안전 하한 (절대 규칙)      TTC <= T_floor -> 무조건 레벨 3

  최종 = max(하한 판정, AI 판정), 상한으로 클램프
```

AI에 안전을 통째로 맡기지 않는다. 모델은 학습 데이터에 없던 상황에서 조용히
틀리므로, 물리로 정한 하한을 그 아래에 깐다.

### T_floor = 2.0초

```
T_floor = GPS 주기 0.2 + 전송 0.1 + 인지·판단 0.3 + 정지 동작 1.2 + 마진 0.2
```

| 항 | 값 | 근거 |
|---|---|---|
| GPS 주기 | 0.2s | NEO-6M 5Hz 전환 후 (1Hz면 1.0s로 올려 잡아야 함) |
| 전송 지연 | 0.1s | **8/5 실측**, 위험도 변경 29건 전수 (계산 1.0ms + 무선 왕복 102ms) |
| 인지·판단 | 0.3s | 촉각 단순반응 0.12~0.18s의 1.5~2배 (선택 반응) |
| 정지 동작 | 1.2s | 보행 급정지 실험 0.84~1.21s (감속 0.91~1.57 m/s²) |

합 2.0초가 **GB/T 33577(ISO 15623 준용) 최소 2초, NHTSA NCAP FCW 2.0~2.4초와
같은 자리**에 떨어진다. 우리 실측·인간 반응 문헌·국제 기준이 독립적으로 같은 값을
가리킨다.

**한계:** 시각장애인이 진동 경보를 받고 멈추기까지의 시간을 직접 잰 연구는 찾지
못했다. 일반 보행자 급정지 데이터로 대용했으며, 발표에서 밝혀야 할 가정이다.

## 3. 정답을 어떻게 만들었나 (오라클)

시뮬레이션은 미래를 안다. 블랙박스를 되감아 "이 순간 경보했어야 했나"를 사후
판정하는 것과 같다.

```
d_min(t) = min{ 거리(τ) : τ ∈ (t, t+3초] }
y(t)     = 1 if d_min(t) ≤ 2.0m else 0
```

TTC도 점수표도 DCPA 게이트도 쓰지 않는다. 좌표 기하학과 미래 정보뿐이다.
`oracle.py`는 `step7_risk` import를 **AST 검사로 차단**해 순환을 구조적으로 막는다.

**교차검증:** 오라클과 PET(Post-Encroachment Time, 교통공학 표준 상충지표)의
판정이 **96.7% 일치**했고, 불일치 5건은 전부 PET가 더 넓게 잡는 방향이었다.
정의가 전혀 다른 두 방법이 같은 답을 내므로 라벨이 특정 수식에 기대지 않는다.

### 창(horizon) 3초의 근거

| 창 | AUC |
|---|---|
| 2.0초 | 0.958 |
| **3.0초** | 0.713 |
| 5.0초 | 0.719 |
| 10.0초 | **0.541** (무작위) |

10초 뒤에 차가 무엇을 할지는 현재 정보에 없다. 그것을 라벨로 삼으면 맞힐 수 없는
문제를 내는 것이다. 반대로 2초는 `T_floor`와 같아 경보할 시간이 0이 된다.
**3초 = T_floor 2.0 + 여유 1.0**이고, 물리 외삽·팀 v3와도 창이 일치한다.

### 학습 라벨은 T_floor만큼 민다

```
평가 기준 y       = 1 if (지금, 3초] 안에 위험      ← 채점용, 밀지 않는다
학습 라벨 y_train = 1 if [2초, 3초] 안에 위험       ← 반응 가능한 것만 정답
```

밀지 않으면 0.5초 뒤 접촉하는 시점도 정답이 되어, **모델이 사람이 반응할 수 없는
시점에 울리는 것을 정답으로 배운다.** 이 한 줄이 결과를 갈랐다(아래 6절).

평가 기준까지 밀면 안 된다 — 코앞 위험에서 울린 경보가 "안전한데 울렸다"로
집계되어 오경보율이 부풀려진다. 늦은 경보는 늦은 것이지 헛경보가 아니다.
같은 이유로 `t_hit`은 창과 무관하게 **실제 접촉 시각**을 쓴다.

## 4. 데이터

**SUMO를 쓰지 않는다.** 기존 SUMO 데이터 12,621행에서 차-보행자 **최소거리가
9.59m**로 위험 사례가 0건이었다.

원인도 규명했다. `Simulation/cloud_server/sumo_config/route.rou.xml`의 차량 타입이
`aggressive_car` 하나인데, `jmIgnoreFoeProb`·`jmDriveAfterRedTime`·`impatience`
같은 **보행자 양보 파라미터가 하나도 설정돼 있지 않다.** `accel`/`decel`/`sigma`만
있어서 다른 차에게는 거칠지만 보행자 앞에서는 여전히 신사다. 보행자도
`pedestrian.rou.xml`에 `p0` 1명·고정 경로뿐이다.

대신 파이썬 2체 운동학 시뮬레이터를 쓴다. 필요한 것은 도로망도 신호도 차량추종
모델도 아니고 "차가 보행자 쪽으로 다양한 각도·속도로 접근하는 궤적"뿐이다.

| | SUMO 데이터 | 새 시뮬레이터 |
|---|---|---|
| 보행자 | 1명, 위치 고유값 1개 | 속도·방향·가감속·선회 랜덤 |
| 차량 | 63대 동시, 속도 중앙값 0.0 | 1대, 정지 16% 포함 |
| 최소거리 | 9.59m (위험 0건) | 0.20m (위험 6.5%) |
| 스텝 | 1초 | 0.1초 |

**GPS 노이즈**는 `auto_pipeline/gps_noise.py`를 재사용한다(Gauss-Markov 1차,
σ=2.5m, 8/1 야외 실측 근거). **정답은 노이즈 없는 참값에서, 피처는 노이즈 낀
관측에서** 만든다 — 젯슨이 현장에서 처하는 상황이 그것이다.

## 5. 피처

가져온 것: 팀 v2의 벡터 특징(`dx, dy, dvx, dvy, dcpa`)과 v3의 물리 외삽
(`phys_min_dist_3s`, `phys_t_cpa_3s`). 둘 다 판단이 옳았다.

새로 넣은 것: `d_closing_dt`(상대 가속), `d_heading_dt`(선회율).
**이것이 없으면 모델이 보는 정보가 물리 외삽과 똑같아진다.** 한 시점의 위치·속도
만으로는 "지금 등속이 아니다"를 알 수 없고, 그러면 등속 가정을 깰 근거가 없다.

뺀 것:
- `risk_score` — 라벨 누수
- 절대 좌표 — "이 지도의 이 지점"은 다른 장소로 일반화되지 않는다
- TTC 센티넬 9999 → **30초 클램프**. 기존 `scaler.json`의 ttc 평균이 6198이 되어
  정규화가 망가져 있었다

### 물리 외삽의 한계 = 모델의 몫

| 조건 | 3초 외삽 오차(중앙) |
|---|---|
| 참값 좌표 | **0.00m** |
| GPS 노이즈 + 단순미분 | 3.22m |
| GPS 노이즈 + 칼만(실제 파이프라인) | **2.92m** |

완벽한 좌표에서는 물리 계산으로 충분하다(오차 0). 현장에서는 오차가 2.92m로
**위험 기준 2.0m보다 크다.** 칼만이 크게 개선하지 못하는 이유는 칼만도 등속
가정이라 물리 외삽과 같은 약점을 공유하기 때문이다. 이 틈이 모델의 자리다.

## 6. 결과

### 무엇이 결과를 갈랐나

| 라벨 | AUC | 적시 경보 (C) | C − A |
|---|---|---|---|
| 창 3초, lead 0 (밀지 않음) | 0.970 | 68.7% | +0.7%p (5시드 중 2승) |
| **창 3초, lead 2.0초** | 0.848 | **83.4%** | **+16.9%p (4승)** |

**AUC가 떨어졌는데 성능은 올랐다.** AUC는 시점별 순위 능력이고 우리 목적은
"첫 경보를 얼마나 일찍 내느냐"다. 라벨을 밀기 전 모델은 *문제는 다 맞히는데
제출이 늦는 학생*이었다. **AUC가 높다고 좋은 모델이 아니다.**

### 모델이 무엇을 보고 판단하나 (치환 중요도)

```
closing_los   0.213  접근 속도        ← 압도적
dy            0.069  상대 위치(남북)
veh_speed     0.057  차량 속도
ttc           0.053  TTC              ← 4위
dx            0.046  상대 위치(동서)
dcpa_m        0.046  최근접 예상거리
d_closing_dt  0.039  상대 가속        ← 신규
ped_speed     0.029  보행자 속도
d_heading_dt  0.022  선회율           ← 신규
```

**TTC는 4번째고 접근속도가 4배 중요하다.** "최적 TTC 값 찾기"가 실패한 이유가
여기 있다 — TTC는 여러 신호 중 하나일 뿐이고, 그것만 잘라내면 나머지를 버린다.
신규 피처 둘이 실제로 쓰이는 것도 확인된다.

### 팀 점수표 검증

배점을 바꿔 실험한 결과(모두 오경보율 1.83%로 통제):

| 배점 | 적시 경보 |
|---|---|
| **현 점수표 30/35/20/10 + DCPA 게이트** | **55.6%** |
| DCPA 게이트만 제거 | 22.2% |
| 33/11/44/12 (모델 중요도 기반 재배점) | 33.3% |
| 0/0/100/0 (접근속도만) | 22.2% |

**① 중요도를 배점으로 옮기면 나빠진다.** 중요도는 "비선형 조합에서 얼마나
활용했나"이지 "선형 배점에서 몇 점"이 아니다.

**② DCPA 게이트가 점수표의 핵심이다.** 빼면 성능이 반토막 난다.

`distance_m`↔`dcpa_m` 상관이 **0.99**라 중복처럼 보이지만, 상관계수는 평균만
본다. 차가 멀 때는 둘이 같이 움직이고, 정작 중요한 순간 — 차가 가까이 접근 중일
때 — 갈린다. **팀 점수표는 잘 만들어졌으며, 모델이 이기는 것은 가중치가 아니라
비선형 조합 덕분이다.**

## 7. 폐기한 방향

**"최적 TTC 임계값을 찾는다"** — 데이터가 아니라고 답했다. 비슷한 적시성에서
TTC 단독 규칙은 오경보를 2배 이상 쓴다(4.29% vs 1.99%). 점수표가 거리·속도·DCPA를
함께 보기 때문이다. 최적화 대상은 임계값이 아니라 **판단 구조**였다.

### 도중에 잡은 함정

1. **라벨 순환** — 정답을 규칙으로 만들어 규칙을 학습 (팀 v1~v3 공통)
2. **라벨 누수** — `risk_score`가 입력 피처에 있음
3. **TTC 센티넬 9999** — `scaler.json`의 ttc 평균 6198, 정규화 파손
4. **분할 쏠림** — 위험 시나리오 5개 중 4개가 평가로 가서 AUC 0.49 → 층화 분할로 수정
5. **기하학적 특이점** — 통과 순간 가속도가 100 m/s²로 튀는 이상치 → 클램프
6. **선회율 균등분포** — 기하학이 무너져 위험 사례 2.4%에 그침 → 확률 구조로 수정
7. **라벨 창 미설정** — 반응 불가능한 경보를 정답으로 학습 (결과를 가른 핵심)

## 9. 상황별 경보 프로필 (`alarm_ttc_by_situation.png`)

발표에서 "그래서 TTC를 몇 초로 정했냐"는 질문에 대한 답이 이 그림이다.

| 상황 | 개수 | TTC가 무한대인 비율 | 경보 여유(중앙) |
|---|---|---|---|
| 측면 · 고속 | 15 | **53%** | 3.10s |
| 후방 · 고속 | 4 | **75%** | 2.65s |
| 정면 · 저속 | 3 | 33% | 4.80s |
| 측면 · 저속 | 6 | 0% | 3.95s |
| 정면 · 고속 | 5 | 0% | 3.50s |
| 정지 차량 | 2 | 0% | 2.30s |

**모델이 잡은 위험의 34%는 TTC가 상한(30초)에 붙은 상태에서 경보됐다.** 옆으로
지나가는 차는 시선방향 접근속도가 0에 가까워 TTC가 무한대로 계산되지만, 곧 앞을
가로지른다. **TTC 임계값을 몇 초로 정하든 원리적으로 걸리지 않는 위험**이고,
"최적 TTC 찾기"가 답이 될 수 없었던 가장 직접적인 이유다.

경보 여유시간도 상황마다 2.30~4.80초로 2배 차이가 난다. 임계값 하나로는 낼 수
없는 폭이다.

## 10. 실외 로그 교차검증

`logs/raw_20260805_190051.log`(cane 9,790 / vehicle 3,995 레코드, 공통 구간 1,080초).

**정답 기반 채점은 불가능하다.** 실외 실험은 안전상 차를 사람에게 붙일 수 없어
위험 라벨이 거의 없다. 대신 두 가지를 확인했다.

### 분포 정합 (차량이 움직인 구간만)

정지 구간을 섞으면 통계가 씻겨 나간다 — 8/5 분석에서 접근속도 편향이 정지 68%
때문에 0으로 희석됐던 것과 같은 함정이라, `veh_speed >= 1.0 m/s` 구간만 봤다.

| 피처 | 실측 | 시뮬레이터 |
|---|---|---|
| 차량 속도 | 1.46 m/s | 7.35 m/s |
| 보행자 속도 | 0.16 m/s | 0.88 m/s |
| 거리 | 59.2m | 46.5m |

**실측이 5배 느리다.** 이는 시뮬레이터 오류가 아니라 실험 제약이다 — 사람이 차

### 거동 타당성

모델이 실측 궤적에서 위험확률 0.5 이상을 낸 구간은 9스텝이었고, 그때의 상황은

말이 되는 시점이다. 다만 9스텝으로는 통계를 말할 수 없다.

## 12. 정직하게 밝힐 것

- 오경보율의 **절대값**은 시뮬레이터 생성 분포 기준이다. "하루 몇 번"으로 해석할
  수 없고, 세 방법의 **상대 비교**로만 읽어야 한다. 실제 빈도는 실외 로그로 확인한다.
- 시각장애인 대상 반응시간 문헌이 없어 일반 보행자 데이터로 대용했다.
- 다중 차량 상황은 다루지 않았다. 현재 `step4_state_store`가 차량 1대만 추적하므로
  시뮬레이터만 다중으로 만들면 실제 시스템과 어긋난다.
- 위험구역(zone)은 넣지 않았다. 오라클 라벨이 물리적 충돌만 보므로, 교차로에서
  실제로 더 자주 충돌하도록 모델링하지 않는 한 정당화되지 않는 가중치가 된다.
