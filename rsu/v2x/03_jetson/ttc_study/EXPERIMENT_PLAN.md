# 실험 계획 — GPS 5Hz 확인 + 안전 하한 검증 + 모델 검증 데이터 확보

작성 2026-08-06 · 목표 실시일 8/17 통합테스트 이전

## 왜 이 실험이 필요한가

지금 세 가지가 확인되지 않은 상태다.

1. **GPS 5Hz 전환이 실제로 반영됐는가.** 배포한 안전 하한 `T_floor = 2.0초`는
   GPS 주기 0.2초를 전제로 계산한 값이다. 1Hz면 필요한 하한이 2.8초가 되어
   전제가 무너진다. 8/5 로그 기준으로는 936ms(1.1Hz)였다.
2. **안전 하한이 실기에서 어떻게 동작하는가.** 시뮬레이션에서는 오경보가
   2.03%에서 3.24%로 늘고 검출이 18/19에서 19/19가 된다. 실기 수치는 없다.
3. **모델 검증에 쓸 표본이 있는가.** 현재 실측 검증은 9스텝뿐이다. 8/5 로그에는
   차량 속도 3 m/s 이상 구간의 접촉 위험이 **0건**이었다.

**한 번의 실험으로 셋을 모두 확인할 수 있다.**

## 목표 수치

| 항목 | 목표 | 확인 방법 |
|---|---|---|
| GPS 갱신 주기 | 200ms 부근 (5Hz) | `verify_experiment.py` 1번 항목 |
| 차량 속도 | **3 m/s(10.8 km/h) 이상** 구간 확보 | 3번 항목 |
| 접촉 위험 이벤트 | **30건 이상** (2m 이내 접근) | 3번 항목 |
| 접근 각도 | 정면 / 측면 / 후방 고르게 | 시나리오 배분 |

**측면 접근을 반드시 포함할 것.** 시뮬레이션에서 측면 위험의 53%가 TTC 무한대
상태였다. 규칙이 놓치고 모델이 잡는 구간이 여기라, 실측으로 확인해야 할 핵심이다.

## 안전 확보 — 사람을 위험에 두지 않는다

**보행자 노드를 사람이 들지 않는다.** 차량을 사람에게 2m까지 접근시키는 실험은
해서는 안 된다. 대신:

- 지팡이 노드를 **삼각대, 카트, 또는 콘 위에** 고정한다 (지면 1.0~1.2m 높이,
  실제 착용 높이와 맞춤)
- 조작자는 **차량 경로 밖**에서 대기한다
- "보행자 이동" 시나리오가 필요하면 노드를 실은 카트를 **줄로 끌어** 움직인다

이렇게 하면 위험 데이터를 안전하게 만들 수 있다. GPS·통신·판정 로직 입장에서는
노드가 사람 손에 있든 삼각대에 있든 동일하다.

**주의:** 차량 노드를 실은 차량은 3 m/s 이상으로 움직여야 하므로, 통행이 없는
공터나 폐쇄된 구역에서 진행한다. 자전거나 전동 킥보드로 대체해도 목표 속도는
충족된다(3~7 m/s).

## 실험 절차

### 준비

1. **차량을 먼저 켠다.** 지팡이 펌웨어는 차량이 만드는 `V2X-LOG` AP에 20초 안에
   접속하지 못하면 재부팅을 반복한다. 순서를 지키지 않으면 지팡이가 ESP-NOW를
   시작조차 못 한다.
2. 브리지 상태 확인: `python3 scripts/check_bridge.py`
   → `bridge_boot version:3` 확인 (v3 프로토콜, 36바이트)
3. 링크 상태 확인: `python3 scripts/watch_link.py` → `READY` 확인
4. 젯슨 엔진 재시작으로 새 로그 시작:
   `sudo systemctl restart v2x-risk-engine`

### 본 실험 — 시나리오 3종 × 10회

각 회차 사이에 5초 이상 간격을 둔다(궤적이 섞이지 않게).

| # | 시나리오 | 접근 | 목표 통과 거리 | 반복 |
|---|---|---|---|---|
| A | 정면 접근 | 노드를 향해 직진 | 0.5~2 m | 10 |
| B | **측면 통과** | 노드 옆을 가로질러 통과 | 1~2 m | 10 |
| C | 사선 접근 | 45도 방향에서 접근 | 0.5~2 m | 10 |

**B가 가장 중요하다.** TTC로는 잡히지 않는 위험이 여기서 나온다.

여유가 있으면 추가:

| # | 시나리오 | 목적 |
|---|---|---|
| D | 스쳐 지나감 (5~10 m) | 오경보 확인 — 울리면 안 되는 상황 |
| E | 접근하다 정지 | 하한이 잘못 발동하는지 확인 |

### 종료

1. `sudo systemctl restart v2x-risk-engine` (로그 마감)
2. 두 번째로 최신인 CSV와 raw 로그를 실험명으로 개명:
   ```
   sudo mv logs/risk_tx_<STAMP>.csv logs/exp_8.X_5Hz검증.csv
   sudo mv logs/raw_<STAMP>.log     logs/exp_8.X_5Hz검증_raw.log
   sudo chown $USER: logs/exp_8.X_5Hz검증*
   ```
   (로그가 root 소유라 sudo가 필요하다)

## 실험 후 검증

PC로 로그를 가져와 한 번에 확인한다.

```bash
python verify_experiment.py --log ../logs/exp_8.X_5Hz검증_raw.log
```

출력 네 항목이 각각 다음을 답한다.

1. **GPS 갱신 주기** — 200ms 부근이면 5Hz 확인. 900ms대면 전환이 반영되지 않은 것.
2. **안전 하한 발동** — 레벨 3 송신 건수. 정확한 판정은 CSV에서
   `ttc_s <= 2.0 && risk_level == 3`인 행을 세면 된다.
3. **표본 수량** — 고속 접촉 이벤트가 30건 이상이면 모델 검증 가능.
4. **섀도우 비교** — 같은 궤적에서 모델과 규칙이 각각 언제 울렸는지. 모델만
   울린 구간이 실제로 위험했는지 육안으로 확인할 수 있다.

## 실험이 실패로 판정되는 경우와 대응

| 증상 | 원인 | 대응 |
|---|---|---|
| GPS가 900ms대 | 5Hz 설정이 반영 안 됨 | 펌웨어의 UBX-CFG-RATE 확인. 보드레이트 9600에서 GGA+RMC만 남겼는지 확인 |
| 지팡이 레코드 없음 | 차량 AP 미기동 또는 브리지 버전 불일치 | 차량 먼저 켜기, `check_bridge.py`로 v3 확인 |
| 브리지 무응답 | 젯슨 USB 전류 부족(브라운아웃) | 다른 포트, 굵은 케이블, 전원공급형 허브 |
| 고속 위험 0건 | 차량이 너무 느리거나 멀리 지나감 | 목표 통과 거리 2m 이내를 지켰는지 확인 |
| 오경보가 과하게 많음 | 안전 하한(TTC 2.0s) 발동 | CSV에서 `reason` 확인. 의도된 동작이며 검출률과 트레이드오프다 |

## 이 실험으로 답할 수 있게 되는 것

- 안전 하한 2.0초의 전제(GPS 5Hz)가 실제로 충족되는가
- 실기 오경보율이 시뮬레이션 예측(3.24%)과 비슷한가
- 모델이 시뮬레이션에서 보인 우위(+16.9%p)가 실측에서도 관찰되는가
- TTC가 무한대인 측면 위험을 모델이 실제로 잡는가 (연구의 핵심 주장)
