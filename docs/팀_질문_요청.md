## 🟣 최민서에게 (AI / SUMO / 위험지도)

**1. 좌표계 (제일 급함)**
- SUMO net.xml이 실제 지역(상도동?)에 지오레퍼런싱 돼 있어? (`netconvert`에 `--proj`나 OSM 썼어?)
- `sumolib.convertXY2LonLat()`로 SUMO(x,y) → 위경도 변환 파라미터(원점/투영) 뽑아줄 수 있어?
- AI 모델 입력 좌표를 **SUMO 로컬 유지**할까, **위경도로 재학습**할까? (실시간은 GPS 위경도라서)

**2. AI 모델(ONNX) — 규격은 내가 파일에서 직접 확인했고, 대신 큰 문제를 하나 찾았어**

먼저, 물어보려던 것들은 리포에 있는 `scaler.json`·`export_onnx.py`·학습 데이터로 다 확인됐어.
(feature 11개 순서 ✓ / window 10 ✓ / 출력은 logits 4개 → argmax, **현재 시점 분류** ✓ /
`ttc` 미접근은 **9999** ✓ — 12,621행 중 7,802행(61.8%)이 9999라 확실해)
모델 파일이랑 scaler도 리포에 이미 있어서 따로 안 줘도 돼. 내 쪽 추론 코드는 이 규격에 맞춰
고쳤어(11 feature + z-score 정규화 + 결측 ttc를 9999로).

**🔴 그런데 학습 데이터를 집계해보니 이게 나왔어:**

| feature | 12,621행에서의 실제 값 |
|---|---|
| `ped_x` | **전부 3600** (고유값 1개) |
| `ped_y` | **전부 1400** (고유값 1개) |
| `ped_speed_mps` | **전부 1.2** (고유값 1개) |
| `risk_level=3` | **30행뿐** (0.24%) |

즉 **보행자가 한 자리에 고정된 데이터로만 학습**돼서, 모델이 "보행자가 움직이는 상황"을
한 번도 못 봤어. 게다가 `scaler.json`을 보면 이 세 개의 `scale`이 전부 `1.0`인데,
이건 sklearn이 표준편차 0일 때 1.0으로 대체한 결과야. 그래서 **정규화가 이 축을 안 눌러줘** —
실시간 좌표를 넣으면 `(x - 3600)`이 그대로 남아서 -3600 같은 값이 되고, 나머지 feature는
z-score라 ±3 범위인데 한 축만 1000배 커져서 예측이 망가져.

→ **이건 좌표계를 어떻게 통일하든 안 풀리는 문제야.** 물어볼 건:
- 보행자를 고정한 게 의도였어? (SUMO에서 안 움직인 건지, 궤적은 있는데 feature 뽑을 때 빠진 건지)
- **움직이는 보행자로 재학습 가능해?** 아니면 어차피 정보가 0인 보행자 3개 feature를 빼고
  차량 중심 8개로 재학습하는 게 나을까?
- `risk_level=3`이 30건뿐인데 그 클래스 성능은 믿을 만해? (test set엔 몇 건 들어갔어?)
- window 10프레임이 몇 Hz야? (SUMO step-length)

그때까지 내 쪽은 **AI를 기본 꺼두고**(모델 미지정 시 자동 비활성) rule+zone만으로 돌릴게.
안전 기능 자체는 그걸로 완결돼.

**3. risk_level 정의 통일**
- risk 0~3을 **점수표 방식**(0~100점 → ≥70:3, ≥45:2, ≥20:1)으로 통일해도 돼? (Transformer가 이걸로 학습됐으니 이게 맞을 듯)
- 아니면 임계값 방식(dist<3/6/10, ttc<1.5/3/5)으로 갈까?

**4. zone 정의 — 파일이 3개라 어느 게 정본?**
- `zones/zone_definition.csv` (center 3600대, speed_limit 있음, Z01~Z04)
- `lux/zone_definition.csv` (center 10/5 같은 작은 값, 스키마 다름)
- `zones/zoneszone_definition.csv` (헤더만, 빈 파일)
- → **정본 하나 지정**해줘. 그리고 base_risk(0~5)→level(0~3) 매핑 `{5→3, 4→2, 3→1, 2→1, 0→0}` 이거 확정?

**5. 위험지도 (han/map)**
- 서버 직접 띄워서 확인해봤는데 업로드/집계는 잘 돌아가. 근데 **버그 하나 찾았어.**
  실시간 지팡이가 실내에서 쓰는 가짜 좌표(37.0/127.0, 상도동에서 55km 밖)를 올려봤더니
  거부를 안 하고 **상도동 도로에 위험도 3으로 찍혀버려.** `roads.py`의 `nearest_edge_id`가
  거리 제한 없이 무조건 제일 가까운 도로에 붙이거든. 지금 상태로 업로드를 붙이면 실내에서
  개발할 때마다 지도가 오염돼.
  → **가장 가까운 도로가 N m(예: 50m) 넘게 떨어지면 저장을 거부**하게 막아줄 수 있어?
    (내 쪽에서도 gps_valid=0이면 안 올리게 막을게)
- lux 파이프라인이 위험 이벤트를 `POST /api/events`로 올리게 붙일게. 서버 주소 뭐로 할까? (로컬 / cloudflared 터널 / 공용)
- 업로드 트리거는? (매 이벤트 / risk≥1만 / 중복 억제)
- `map`이 지금 어느 리포에도 커밋이 안 돼 있는데, 정본 리포에 넣을까?
- SUMO 결과를 지도에 올리는 스크립트(`import_sumo_results.py`)는 이미 있는데, 지금 리포에
  있는 건 4줄짜리 포맷 예시뿐이야. **실제 SUMO 결과 CSV를 위경도로 변환해서 한 번 올려볼 수
  있어?** (좌표계 질문 1번이 풀려야 되는 거라 그거랑 같이)

## 🔵 박중선에게 (하드웨어)

**1. 펌웨어 버전 통일**
- 무선 구조체 `V2X_VERSION`이 사본마다 1/2로 달랐어. 지금 정본(github=최신)은 **2**야. 네가 들고 있는 차량/지팡이/RSU 보드 **전부 최신(V2)으로 재플래시** 돼 있어? (버전 다르면 패킷 자체를 서로 버려서 통신 안 됨)

**2. 브리지 표준**
- RSU 브리지 여러 버전(05/08/10) 중 **파일 10(멀티 브리지)**를 표준으로 갈게. cane/vehicle 같은 키에 node_risk 포함이라 Jetson이랑 제일 잘 맞아. 이걸로 확정해도 돼?

**2-1. RSU에 실제로 올라가 있는 브리지 펌웨어 버전 확인해줘 (좀 이상한 게 있어)**
- Jetson에서 risk를 내려보낼 때 `{"target_id":0,"risk":N}` 형태로 보내고 있었는데,
  리포의 파일 10 코드를 뜯어보니 **`target_id:0`은 브로드캐스트가 아니라 "node_id 0번 단말에게"로
  읽혀서 그런 단말이 없으니 그냥 버려지는(risk_drop)** 게 맞아. 브로드캐스트하려면 **키를 아예 빼야** 해.
  → 내 쪽 코드는 키를 빼도록 이미 고쳤어.
- **그런데** 지난번 실기 테스트 기록엔 그 형식으로 보냈는데도 RSU가 `risk_broadcast_to_seen`으로
  응답했고 지팡이 risk도 따라왔다고 남아 있어. 코드대로면 안 되는 일이야.
  → **RSU 보드에 지금 올라가 있는 브리지 펌웨어가 리포 파일 10이랑 다른 (예전) 버전일 가능성**이 커.
    보드에 뭐가 플래시돼 있는지 확인해줄 수 있어? (1번 V2X_VERSION 문제랑 같은 뿌리일 수도)

**3. 액추에이터 핀 충돌**
- 진동/부저 핀이 코드마다 달라(GPIO26/25 vs 25/27). **최종 배선 하나**로 확정해줘.

**4. 음성(DFPlayer)**
- DFPlayer 음성 재생이 실제로 되는 상태야? (미팅 노트엔 "0001~0004.mp3 분기 성공"인데 저장소엔 재생 코드가 안 보여서)
- 트랙 번호 ↔ risk 매핑 어떻게 돼 있어?
